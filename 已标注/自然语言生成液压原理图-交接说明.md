# 自然语言生成液压原理图：交接说明

## 1. 要解决的问题

最初目标是从组件库 SVG 绘制液压原理图，并让 JSON 成为后续生成的唯一依据。实际操作暴露出一个矛盾：

- 若工程师逐项维护组件、端口、网络、装配成员、仪表测点和功能关系，JSON 很清晰，但人工工作量过大且容易漏项。
- 若 AI 只根据图形或模糊描述自由画线，关系会不清晰，且容易把图形相邻误当成液压连接。

当前方案的结论是：**工程师用自然语言表达系统意图；AI 将意图编译为带来源追溯的 L2 草案 JSON；工程师审查“关系表”，而不是手写 JSON。**

## 2. 已形成的模型

```text
自然语言系统描述
  → Semantic Claims（带原句的语义声明）
  → 组件目录与受控装配模板匹配
  → L2 草案 JSON（拓扑事实候选）
  → 审查卡（组件 / 网络 / 仪表 / 功能 / 待决项）
  → 已确认 L2
  → L3 拓扑、L4 布局、L5 SVG/连接表/校核报告
```

L1 组件目录、L2 系统拓扑、L4 布局和 SVG 保持分层：AI 可提出布局，但不得改变 L2 拓扑。

## 3. 关系的明确表达

不要用一条泛化的“组件 A 连组件 B”同时表达所有含义。当前模型把关系拆为四类：

| 关系 | JSON 位置 | 例子 |
|---|---|---|
| 物理流体连通 | `nets`、`internal_nets` | `CV-001.inlet` 和 `PS-001.pressure_sense` 属于同一压力网络 |
| 仪表测量 | `instrumentation_relationships` | `PS-001` 经该网络测量 `CV-001.inlet` 上游压力 |
| 功能行为 | `member_relations` 或 L1 模板 | 单向阀阻断反流；溢流阀泄放 |
| 封装与接口 | `members`、`published_ports` | 外部只连 `ASM-001.inlet_1`，不能直接连内部 `CV-001` |

这使“压力开关与单向阀的关系”不再模糊：压力开关不是主油路串联元件，而是以指定端口测量指定网络中单向阀入口侧的压力。

## 4. 已完成的示例

示例是一个不可现场拆分的双入口总成：两个压力开关、两个单向阀、一个过滤器和一个溢流阀。

```text
IN-001 → ASM.inlet_1 → CV-001 → ┐
                                  ├→ F-001 → OUT-001
IN-002 → ASM.inlet_2 → CV-002 → ┘            └→ RV-001 → RET-001

PS-001 测量 CV-001.inlet 上游压力
PS-002 测量 CV-002.inlet 上游压力
```

已生成并校核：6 个装配成员、5 条内部网络、2 条显式仪表关系、3 条功能关系、8 条自然语言来源声明，以及 JSON 到 SVG 的 ID 追溯。

## 6. 尚未实现，不应误称为能力

目前是已验证的模型、样例和规范，不是已交付的软件生成器。尚缺：

1. 版本化的 `component-catalog.json`，其中需定义端口、允许通流方向、仪表能力和受控总成模板；
2. 自然语言到 `claims` 的提取器；
3. `claims` 到 L2 的确定性编译器；
4. JSON Schema 与端口/介质/通流方向/仪表测点校核器；
5. 审查卡、差异表和审批状态机；
6. L2 到 L3/L4/L5 的正式拓扑、布局、渲染与回读校核实现。

因此现有 SVG 只可标为 `CONCEPT - NOT FOR DESIGN RELEASE`。

## 7. 建议实现顺序

1. 先冻结一个 10–20 种组件的 L1 目录和 3–5 个总成模板。
2. 定义受控 `claims` 词汇：串联、分支、汇合、回油、泄放、取压、装配、外部接口。
3. 先支持“自然语言 + 明确术语”的受限输入，不尝试任意长文或图像理解。
4. 构建确定性 L2 编译器；所有 AI 推断写入 `catalog_inference`，所有模糊关系生成待决项。
5. 先交付审查卡和 JSON 差异表，再接 SVG 生成。
6. 建立金样例与回归测试；通过后才扩组件和自由度。

## 8. 下一 task 的推荐起点

先完成实现方案的 grill，明确 L1 目录来源、首批受支持范围、工程师审查责任、审批/配置管理边界和 MVP 验收标准；再实现一个受限语言的 vertical slice。
